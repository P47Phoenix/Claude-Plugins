## What Changed

The Architect skill now includes a mandatory **Prior Art Analysis** step that executes before any design work begins. When a user provides specifications or an existing design, the Architect must:

1. **Read and summarize** all user-provided specs before proposing architecture
2. **Classify each element** as either "Decision Already Made" or "Open Question" in a structured table
3. **Build on the existing design** — validate feasibility, fill gaps, and map to implementation
4. **Justify any deviations** — alternatives to settled decisions are only permitted when a specific, documented technical blocker makes the original decision infeasible

When no user-provided specs exist, the step notes their absence and proceeds normally. Existing pipelines are unaffected.

## Why It Changed

Previously, the Architect agent would propose competing designs instead of building on user-provided specifications. When a user handed the team a detailed spec (e.g., a multi-agent system design), the Architect would reimagine the solution from scratch rather than validating and extending it. This eroded user trust and wasted pipeline cycles on unnecessary self-correction loops.

## Impact

- **Who benefits**: Plugin developers and delivery pipeline users who provide detailed specifications or existing designs as input. The Architect now respects established design decisions by default.
- **Breaking changes**: None. The Prior Art Analysis step is conditional — it activates only when user-provided specs are present. Pipelines without user specs see no behavioral change.
- **Scope limitation**: This fix addresses the Architect skill only. Other skills (developer, quality, operations, etc.) are not modified. If similar "override user intent" patterns exist in other skills, those would require separate fixes.
