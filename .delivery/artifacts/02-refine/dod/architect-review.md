## Findings

1. **Line-budget headroom (S2/S3, FR-2.5, G6).** `delivery-team/skills/delivery-flow/SKILL.md` is 499 lines against a 500 budget, and `delivery-team/skills/product-delivery/SKILL.md` is exactly 300 against a Tier B 300 budget. FR-2.5 requires ADDED lines (a conditional "latest Opus" line and a `dod_validators` cap line) in delivery-flow, on top of rewriting the 4.7 blocks at lines 27 to 30 and 273 to 276. The PRD never says the S2 rewrite must be net-neutral or negative in lines. Required fix: add to FR-2.5 and FR-3.1 an explicit constraint that the net line delta of delivery-flow is at most +1 and of product-delivery at most 0 (offset by tightening the removed 4.7 blocks), and make S2 run `python3 scripts/check_skill_budgets.py` at its own close, not only S3. Otherwise a `Budget-Exception:` protocol, which does not fit a no-PR ship, becomes the only way out.

2. **`model_usage.*` and `tokens.cache_hit_ratio` are not collected by the baseline today (FR-5.1, FR-5.7).** `baseline.py::_collect_metric_values` walks only `HARD_METRIC_KEYS`, `ADVISORY_METRIC_KEYS` and `skill_loads.*`, and `_check_hard_rules` / `_check_advisory_rules` already ignore anything else. So the PRD's "skip model_usage.* in the two check functions" is a no-op, while the real work is unstated: the dynamic keys must be explicitly collected into `metrics` with a new classification (for example `informational`) so AC-5.1 can find them, and `_classify` must not turn them into hard or advisory. Also, flattened dotted keys break on real provider-prefixed IDs (Bedrock forms contain dots and colons, for example `anthropic.<id>-v1:0`) if any code splits on `.` (as `_extract_metric` and the advisory branch do for `skill_loads.`). Required fix: state in FR-5.1/FR-5.7 that `baseline.py` gains a dynamic-key collection with an explicit non-thresholded classification, and either store `model_usage` as a nested object keyed by model (preferred; AC-5.1 adapts) or require key handling that never splits on the model part.

3. **Parser double counting on split assistant events (FR-5.9, AC-5.9).** The PO's own real capture shows 2 `assistant` events for a single one-word reply. That pattern is what Claude Code emits when one API message is streamed as several events (thinking block, then text block) that share one `message.id`, each repeating `message.usage`. Counting per assistant event overstates `dispatch_count`, per-model `dispatches` and token sums; adding the `result` aggregate on top double counts again. FR-5.9 says only "does not double count the result aggregate", and AC-5.9 asserts merely `dispatch_count >= 1`. Required fix: FR-5.9 names the rule (tokens and cost from the `result` event `usage` / `modelUsage`; dispatches counted as distinct `message.id` values, deduplicated), and AC-5.9 asserts `dispatch_count` equals the distinct-id count of the real fixture and that summed tokens equal the `result` totals. Without this the cache-hit ratio in the 5-sample baseline can be silently wrong.

4. **Producer/validator coupling to an interface that does not exist yet (FR-4.4, FR-5.4b, AC-5.5b, AC-5.9b).** The validator must write `test_cmd_has_max_budget`, `test_running_cost_reads_total_cost_usd`, capture-failure and `--init-baseline` consistency tests against functions whose signatures the producer has not written: `_build_claude_command(workspace, prompt_path)` today takes no model, effort or cost cap, and the capture entry point and its error type are unnamed. Yet FR-4.4 requires the tests to be red first and `lib/` to be unchanged from `validator_start` to `validator_end`. The two constraints collide unless the interface is fixed beforehand. Required fix: Stage 4 design (or the S5 preface) pins the contract: function names, parameters, return shape, and the exit codes for capture failure and consistency failure; and S5 ordering is stated as producer interface stub commit, then validator dispatch (start SHA after the stub, red tests), then producer fix. AC-4.4's disjoint `lib/` versus tests commit sets still hold under that order.

5. **Ship-time gate is a process gate, not a mechanical one (FR-1.1, FR-1.5, FR-7.3).** The design is sound and honestly stated: the push workflow detects after the push, the hook is opt-in (`core.hooksPath`) and advisory by default, and the strict step is a manual local run recorded in the S7 report. Feasible, but nothing mechanical stops a direct push with hits (the S7 executor can skip step 2). Required fix (low cost): add an opt-in `.githooks/pre-push` that runs `python3 scripts/check_model_pins.py` strictly, or record explicitly that the S7 report line `check_model_pins.py exit=0` is the sole control and the reviewer of the ship must inspect it. Also note the existing hook runs under `set -euo pipefail`; the staged-file invocation must tolerate zero staged files and deleted paths (use `git diff --cached --name-only --diff-filter=ACMR`, NUL-safe) or the advisory call can abort the commit.

6. **`--max-budget-usd` result handling (FR-5.4).** When the CLI stops a run on budget, the terminal `result` event carries an error subtype (not `success`) and may lack fields the capture requires. The PRD does not say how the runner maps this: it must classify it as cost-cap exit code 2 (not plumbing 4), must not feed the truncated sample into `--init-baseline`, and must keep the `model_resolved` failure rule from misreporting it as "no model". Also the CLI checks the budget between turns, so the cap can be exceeded slightly; NFR-1 ("<= $3.00") is then enforced by the harness post-check, which the PRD already provides in layer 2. Required fix: one sentence in FR-5.4 naming the result-subtype mapping and that an over-cap sample aborts `--init-baseline`.

7. **Baseline schema version (FR-5.5).** Six new top-level fields (`model_requested`, `model_resolved`, `model_pin_env`, `effort`, `host_context`, `samples`) are added while `SCHEMA_VERSION` stays `"1"`, and `host_context.claude_code_version` duplicates the existing `last_captured_cli_version`. Required fix: bump `SCHEMA_VERSION` to `"2"` (the baseline is re-captured and not merged, FR-5.6, so no compatibility burden), make `baseline.py` reject a version-1 baseline with a clear re-capture message, and either drop the duplicate CLI-version field or state which is authoritative.

8. **Base-ref fragility of PRE-SHIP ACs (AC-2.1, AC-2.5, AC-4.4, AC-5.9b).** They use the moving local ref `main` (`git show main:<file>` with hard-coded line numbers, `git diff main`, `git log main..HEAD`, `git archive main`). If `main` advances during the multi-story run (version bumps and other sessions ff-merge to main), the named line numbers in AC-2.1 shift and `git diff main` includes unrelated edits. Required fix: record `base_sha=$(git merge-base main HEAD)` once at S1 (for example in `.delivery/artifacts/06-development/base-sha.txt`) and have these four ACs use that SHA. Related note for S5/S6: the baseline is captured against the S2/S3 prose; any DoD rework of a SKILL.md after S5 silently changes what the baseline measured (S7 step 5 protects the fingerprint but not baseline representativeness). State that SKILL.md edits after S5 require a re-capture or an explicit waiver.

9. **Guard scope side effects to state in S1 (FR-1.2, Rule A/B).** (a) Rule B runs over every `*.md`, so any documentation the S1 story writes about the guard (governance note, script docstring examples in `.md`, README) must itself contain no version examples; state this in FR-1.2 so S1 does not fail its own AC-1.2c. (b) `PIN_RE` flags any `claude-...<digit>` token, including non-model identifiers such as a plugin or skill name like `claude-code-v2`; with no escape the remedy is rewording, which is accepted but should be listed under "Accepted loopholes" as a known false-positive class. (c) Later S5 additions in scope (`tests/test_model_capture.py`, smoke README/ARCHITECTURE) can re-introduce concrete IDs after the S4 gate closes; the S7 strict run catches it, but the validator dispatch instructions should say tests derive model strings from the fixture or use synthetic IDs, never literals.

## Confirmed sound (no action)

- `MODEL_TIER_ALIAS` as one Python dict plus the alias/API-ID split is feasible and consistent with the docs evidence; no repo code calls the API (FR-4.5), and the `flow_orchestrator.py:663` latent trap is addressed. Frontmatter aliases (9 lines) are honestly held to a vocabulary rather than a single location.
- Guard scope via `git ls-files --cached --others --exclude-standard` with `isfile` filtering makes local, canonical count and ship gate agree, and works in a clean CI checkout; nested worktree directories are skipped as non-files. JSON exclusion and the fixture-in-JSON approach avoid self-tripping. Script self-scan is clean (`PIN_RE` and `STAMP_RE` do not match their own source text).
- Existing `stale-model-id-guard.yml` is a `pull_request`-only paths-filtered workflow; the rewrite (push, pull_request, workflow_dispatch, no filter) is compatible with `workflow-injection-lint.yml`, adds no `claude` CLI, and needs no new dependency. `skill-line-budget.yml` is PR-only too, so the local S7 budget run is correctly part of the ship gate.
- Cache fingerprint: single-file sha256 in `governance/cache-prefix-hash.txt`, no consumer besides the fitness-review ledger; version-free content makes it release-stable. S6 after S3 and re-check at S7 step 5 is the correct ordering. ADR before S6 is a Stage 4 dependency already tracked.
- Story order S1 to S7 has consistent preconditions (guard first, prose before stamps, code sweep closes G-LIT, harness after fixtures, fingerprint after all SKILL.md edits, ship last). AC-DISP with negative self-test and non-vacuous REQUIRED list is well-formed.
- Real-shape fixture with provenance sidecar, trimmed `system/init`, raw-stream hashes in `samples`, and `unknown`-as-absent failure rule are feasible and address the observed parser defect.
