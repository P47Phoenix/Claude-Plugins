# ADR-002: Scryfall API Client -- Python Script vs. MCP Server

## Status

Accepted

## Date

2026-04-01

## Deciders

Celebrimbor (Solution Architect)

## Context

The MTG Commander Deck Builder requires a Card Finder utility that queries the Scryfall API for card data, pricing, and validation. Two implementation approaches were considered:

**Option A: Python script (`scripts/card_lookup.py`)** invoked via the `Bash` tool.
- Single Python file using only standard library (`urllib.request`, `json`, `time`)
- CLI interface with subcommands: `validate`, `search`, `batch`, `price`, `batch-price`
- Each agent invokes it via `Bash` tool as needed
- Rate limiting implemented in the script

**Option B: MCP server** registered in `.mcp.json`.
- Persistent server process exposing Scryfall operations as MCP tools
- Agents call Scryfall via MCP tool calls instead of Bash
- Rate limiting managed by the server process
- Connection lifecycle managed by Claude Code

## Decision

**Option A: Python script via Bash tool.**

Rationale:

1. **No external dependencies.** The script uses only Python standard library. An MCP server typically requires a framework (e.g., `mcp` Python package) or at minimum a socket/HTTP server implementation, introducing dependencies the PRD explicitly prohibits (NFR-02).

2. **Simpler deployment.** The script is a single file that works immediately. No server process to start, no port management, no connection lifecycle.

3. **Sufficient for v1 volumes.** A deck build pipeline makes ~5-10 Scryfall API calls (2 batch requests for 100 cards, plus targeted searches for replacements). The overhead of spawning a Python process per call is negligible at this scale.

4. **Follows existing patterns.** The delivery-team plugin's scripts directory contains Python utilities invoked via Bash. No existing plugin in this repo uses an MCP server for a single external API.

5. **Rate limiting is stateless between calls.** Each `card_lookup.py` invocation is a separate process, so rate limiting state (last request time) does not persist between calls. This is acceptable because: (a) Scryfall's rate limit is 10 req/s which is generous, (b) the natural latency of spawning a Python process provides implicit throttling, and (c) the script enforces a minimum delay within batch operations where multiple requests happen in a single invocation.

## Consequences

**Easier:**
- Zero setup. No server process, no `.mcp.json` configuration, no dependency installation.
- Portable. The script works on any system with Python 3.x.
- Testable. Can be tested standalone from the command line without Claude Code.
- Debuggable. Agents see the full stdout/stderr from the script.

**Harder:**
- Rate limiting between separate invocations is not enforced. If multiple agents invoke `card_lookup.py` in rapid succession (unlikely in a sequential pipeline), they could briefly exceed Scryfall's rate limit. Mitigated by the sequential pipeline design and Scryfall's generous 10 req/s limit.
- If a future version adds multiple plugins that all need Scryfall access, an MCP server would centralize rate limiting and connection management. This is the trigger for migrating to Option B.
- No persistent connection pooling. Each invocation opens and closes HTTP connections. Negligible performance impact at v1 volumes.
