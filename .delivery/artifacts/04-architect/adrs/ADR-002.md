# ADR-002: 4-Layer Rule Resolution with Last-Writer-Wins

**Status**: Proposed
**Date**: 2026-03-28
**Author**: Celebrimbor, Solution Architect
**Traces To**: PRD DD2, US-04, US-06, FR-16

---

## Context

The rules engine needs to support multiple sources of rule configuration:
1. Plugin-shipped defaults (routing tables, DoD gates)
2. Named presets (solo, standard, strict)
3. Per-repo customization (`.delivery/config.yml`)
4. Per-run ephemeral overrides (natural language in-session)

These sources may define conflicting values for the same rule parameter (e.g., the default pass threshold is 80, the preset says 70, and the config says 90). A resolution strategy is required.

## Decision

We adopt a **4-layer resolution model with last-writer-wins semantics**.

Layers are resolved bottom-up: Layer 1 (plugin defaults) is loaded first, then Layer 2 (preset) overlays it, then Layer 3 (per-repo config) overlays that, then Layer 4 (runtime) overlays the result. At each layer, the merge semantics are:

- **Scalars**: Higher layer replaces lower layer entirely.
- **Lists**: Higher layer replaces lower layer entirely by default. Opt-in `_merge: extend` appends.
- **Maps**: Shallow merge. Higher layer keys override matching lower layer keys. Unmentioned keys are preserved from the lower layer.

Layer 4 has additional constraints:
- Disabled entirely in strict mode.
- Cannot apply preset-level changes (cannot swap `rules.preset`).
- Can only adjust individual thresholds, toggle validators, or modify escalation sensitivity.
- When relaxing a Layer 3 value, the orchestrator displays a confirmation prompt.

## Rationale

### Why last-writer-wins?

Three resolution strategies were considered:

| Strategy | How it works | Mental model complexity |
|----------|-------------|----------------------|
| **Last-writer-wins** | Higher layer replaces lower for the same key | Simple: "my config overrides the preset" |
| **Merge-all** | All layers are deep-merged, conflicts produce arrays of values | Complex: "what does it mean when three layers define different thresholds?" |
| **Most-specific-wins** | Rules with more specific conditions (e.g., per-stage) beat general rules | Medium: requires understanding specificity ranking |

**Last-writer-wins was chosen because the mental model is trivially explainable.** A user who sets `rules.pass_threshold.design: 90` in their config knows with certainty that the design gate threshold is 90. They do not need to understand whether the preset also defines a design threshold, or whether a more specific rule might override theirs.

This matches the precedent set by CSS specificity (later rules win when specificity is equal) and configuration override patterns in tools like Docker Compose, Kubernetes (last-applied wins), and npm (project-level overrides registry defaults).

**Merge-all was rejected because** it produces ambiguous results. If Layer 1 says `pass_threshold: 80` and Layer 2 says `pass_threshold: 70`, merge-all would need to decide: which one? The answer is the same as last-writer-wins, so merge-all adds complexity without adding value. For lists, merge-all creates even more confusion -- does `required_validators: [dev, qa]` at Layer 2 mean "add these to Layer 1's list" or "replace Layer 1's list"? Last-writer-wins avoids this ambiguity (replace by default, explicit `_merge: extend` for append).

**Most-specific-wins was rejected because** it requires a specificity ranking that is not intuitive for rule configuration. In CSS, specificity is well-defined (element < class < ID < inline). For rules, there is no natural specificity hierarchy between "preset says 70" and "config says 90." Both are equally specific -- they just come from different sources. Layer ordering is simpler and more predictable.

### Why 4 layers specifically?

Each layer serves a distinct persona need identified in the PRD:

| Layer | Persona served | Why it cannot be collapsed |
|-------|---------------|--------------------------|
| 1. Plugin defaults | All (baseline behavior) | Must exist for zero-config operation (NFR-04) |
| 2. Presets | Sarah (solo), Jake (game-dev) | Named profiles reduce config surface for most users. Cannot be per-repo (shared across plugin) |
| 3. Per-repo config | Marcus (team lead), Chen (DevOps) | Team-specific overrides version-controlled with the project |
| 4. Runtime | All (ad-hoc adjustments) | Session-scoped flexibility. Cannot be persisted (would cause drift from checked-in config) |

Collapsing Layers 1 and 2 (presets as part of defaults) was considered but rejected because presets need to be selectable by name (`rules.preset: solo`), which requires them to be separate from the base defaults they override.

Collapsing Layers 3 and 4 (runtime as part of config) was considered but rejected because Layer 4 is ephemeral by design. Persisting runtime overrides would create drift between the config file (version-controlled) and actual pipeline behavior (includes transient changes). This is exactly the class of problem the rules engine is designed to prevent.

### Why is Layer 4 constrained?

Layer 4 accepts natural language overrides parsed by the AI, which makes it the only non-deterministic layer. Constraints minimize the blast radius:

- **Strict mode disables it entirely**: Priya's regulated environment cannot accept AI-parsed rule modifications.
- **Granular only**: Cannot swap presets (which would cascade to dozens of rule changes). Can only adjust individual keys.
- **Relaxation requires confirmation**: Prevents accidental weakening of explicitly configured thresholds.

## Consequences

- Resolution is deterministic for Layers 1-3 (all from files). Layer 4 introduces a hybrid step (AI-parsed input enters deterministic merge).
- The `--dry-run` output shows the resolution layer for every active rule, making the override chain visible and debuggable.
- Adding a Layer 5 in the future (e.g., CI/CD environment-level overrides) would slot naturally between Layers 3 and 4 without disrupting the model.
- Shallow merge for maps means nested overrides require repeating the full nested structure. This is intentional -- it prevents partial merges that silently inherit stale values from lower layers.

## Alternatives Considered

### A1: Single-Layer with Full Config

All rules defined in `.delivery/config.yml`, no presets, no defaults.

**Rejected because**: Violates NFR-04 (backward compatibility). Existing configs with no `rules` section would fail. Also violates the solo developer persona need -- Sarah should not have to configure 126 routing rules to use the pipeline.

### A2: Two Layers (Defaults + Config)

No presets, no runtime overrides. Just plugin defaults and per-repo config.

**Rejected because**: Presets (Layer 2) serve 80% of users who want curated behavior without per-key configuration. Forcing them to replicate preset values in their config is unnecessary configuration burden. Runtime overrides (Layer 4) serve the "just this once" workflow that all personas mentioned in interviews.
