# ADR-002: kicad-happy Integration Pattern -- Cross-Plugin Invocation vs Reference Embedding

**Status:** Accepted
**Date:** 2026-04-12
**Deciders:** Solution Architect (Celebrimbor)
**Pipeline:** run-2026-04-12-hw01 | **Type:** GREENFIELD

---

> "One does not forge a new ring when a ring of power already exists. One learns to wield it. The kicad-happy skills are rings forged by another hand -- we shall not remake them, but we shall bind them to our purpose through the Skill tool."

---

## Context

The hardware-team plugin needs to leverage 11 existing kicad-happy skills:

- **Component sourcing**: digikey, mouser, lcsc, element14
- **Fabrication**: jlcpcb, pcbway
- **Analysis**: kicad, spice, emc
- **Documentation**: kidoc, bom

These skills are installed separately via the Claude Code plugin system at `~/.claude/plugins/cache/kicad-happy/`. The question is how hardware-team role skills should access kicad-happy capabilities.

Two primary options exist:

1. **Cross-plugin skill invocation**: Use the Skill tool with `kicad-happy:<skill>` syntax to load kicad-happy skills at runtime
2. **Reference embedding**: Copy kicad-happy reference content into hardware-team reference files and use it directly without invoking kicad-happy

## Decision

**Use cross-plugin skill invocation via the Skill tool.** Hardware-team role skills invoke `kicad-happy:<skill>` at runtime when they need a kicad-happy capability. No kicad-happy content is duplicated in hardware-team.

**Verification**: Cross-plugin invocation has been confirmed working via live test. `kicad-happy:kicad` loads successfully from `C:\Users\micha\.claude\plugins\cache\kicad-happy\kicad-happy\1.2.0\` (PRD C1 resolution).

**Invocation ownership**: Role skills (not the orchestrator) decide when to invoke kicad-happy skills. The EE skill knows that component selection requires `kicad-happy:digikey`; the orchestrator knows only that the EE skill handles the Schematic stage.

**Error handling**: If a kicad-happy skill is unavailable (not installed), the sub-agent:
1. Catches the Skill tool error
2. Reports `SKILL_UNAVAILABLE` with the skill name, purpose, and install instructions
3. Documents what it could not do (graceful degradation)
4. The pipeline continues with reduced capability rather than crashing

**Reimplementation guard (NFR-003)**: Each role SKILL.md includes a "kicad-happy Consumption" section that:
- Lists which kicad-happy skills it invokes and when
- Explicitly states: "Do NOT parse KiCad files, query distributor APIs, or implement EMC rules directly. Invoke the corresponding kicad-happy skill instead."
- Defines what IS and IS NOT reimplementation (per operational definition in PRD Story 3.1)

## Consequences

### What becomes easier

- **No duplication**: kicad-happy capabilities are maintained in one place; hardware-team gets updates automatically when kicad-happy is updated
- **Clear responsibility**: kicad-happy owns tool capabilities; hardware-team owns orchestration and domain judgment
- **Independent versioning**: hardware-team and kicad-happy can evolve independently; compatibility tracked via `dependencies.kicad_happy_version` in config
- **Smaller plugin size**: hardware-team contains only orchestration logic and domain knowledge, not duplicated tool code

### What becomes harder

- **External dependency**: hardware-team requires kicad-happy to be installed separately; SessionStart hook mitigates this with early warning
- **Version coupling**: kicad-happy interface changes could break hardware-team dispatch; config version tracking and integration layer documentation mitigate this
- **Debugging**: Issues may span plugin boundaries; the orchestrator must clearly log which kicad-happy skill was invoked and what it returned

## Reversibility

**One-way door.** This decision is difficult to reverse. Switching from cross-plugin skill invocation to reference embedding would require:

1. Copying all 11 kicad-happy skill reference content into hardware-team role reference directories
2. Rewriting every role SKILL.md to remove Skill tool invocations and replace them with direct reference loading
3. Removing the reimplementation guards (they would no longer apply)
4. Accepting the maintenance burden of keeping embedded references synchronized with kicad-happy updates
5. Accepting the violation of NFR-003 (no reimplementation of kicad-happy capabilities)

The reverse direction (embedding to cross-plugin) is equally costly. This is a foundational architectural decision that shapes every role skill. It should be treated as a commitment.

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|---|---|---|---|
| Reference embedding (copy kicad-happy references into hardware-team) | No external dependency; always available | Violates NFR-003 (reimplementation); creates maintenance burden (two copies of same content); loses kicad-happy updates; bloats hardware-team context | Directly contradicts the PRD's core design principle |
| Thin wrapper scripts (Python scripts that call kicad-happy CLI) | Programmatic interface; testable | kicad-happy skills are not CLI tools; they are SKILL.md files loaded by the Skill tool; would require reimplementing the invocation | Architecture mismatch -- skills are not CLI programs |
| MCP server integration (expose kicad-happy as MCP tools) | Structured tool interface | Over-engineering for plugin-to-plugin communication; Skill tool already works; adds infrastructure complexity | Unnecessary complexity when Skill tool is sufficient |
