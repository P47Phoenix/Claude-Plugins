# ADR-lmr-004: Smoke harness model-capture contract (parser, interfaces, baseline schema, cost cap)

- **Status**: Proposed (flips to Accepted when Stage 4 DoD passes)
- **Date**: 2026-09-20
- **Run**: run-2026-05-28-o48m, BACKLOG-108
- **Owner**: Solution Architect (PRD S5: FR-5.1 to FR-5.10, FR-4.4, BINDING-4.5; Architect DoD round-2 findings F2, F3, F4, F6, F7)

## Context

The PRD fixes what S5 must achieve. Round-2 Architect review found four gaps the PRD leaves to the implementer, and reading the current `delivery-team/tests/smoke/` code (this stage) found four more constraints. This ADR pins the contract so the producer and the separate validator dispatch (BINDING-4.5) can work against the same interface, and so the red-first test can exist before the fix.

Evidence read in this stage:
- `lib/metrics.py::parse_stream` reads `event.get("usage")` and `event.get("model")` at top level only, counts every `assistant|message|tool_use|result` event that has usage as one dispatch, and buckets a missing model as `"unknown"`. Real streams (PRD S5 table, one local capture on CLI 2.1.278) nest model and usage under `message`, carry the model on `system/init`, and put cost only on the final `result` (`total_cost_usd`, `modelUsage`).
- `lib/runner.py::_running_cost` sums per-event `usage.cost_usd`; `_build_claude_command(workspace, prompt_path)` takes no model, effort or cap.
- `lib/baseline.py::_collect_metric_values` collects only `HARD_METRIC_KEYS`, `ADVISORY_METRIC_KEYS` and `skill_loads.*`; `_check_advisory_rules` already ignores every other key. Consequence: the PRD's "skip `model_usage.*` in the two check functions" is a no-op. The real work is to COLLECT the dynamic keys into `metrics` so AC-5.1 can find them, with a classification that never becomes hard or advisory.
- `run_smoke.py::_execute_single_run` loads `--baseline` from disk for every sample, including during `--init-baseline`, and calls `compare()` when the run exit is 0. During re-capture that would compare each new sample against the invalidated old baseline.
- `tests/test_meta.py` (must stay at exactly 3 tests, AC-4.2 requires it to pass) feeds legacy flat events (top-level `model` and `usage`, `assistant, assistant, result`) and asserts `dispatch_count == 3`, `cost_usd == 0.30` (summed `usage.cost_usd`), tokens summed. `tests/conftest.py` has an autouse fixture that makes any `subprocess` call whose first token is `claude` raise `AssertionError`. `lib/baseline.py::_claude_cli_version()` and `lib/report.py::_claude_cli_version()` run `claude --version`, so a test that calls `init_baseline` or `build_report` without patching them fails.
- `system/init` reports the model: docs https://code.claude.com/docs/en/headless ("The `system/init` event reports session metadata including the model, tools, MCP servers, and loaded plugins.", fetched 2026-09-20). The docs do not name the field; top-level `model` is OBSERVED on CLI 2.1.278 only (PRD table). Subagent messages appear in the stream as `assistant` and `user` messages whose `parent_tool_use_id` is the spawning tool call, `null` for the main conversation (same page). `message.id` on assistant events and the exact budget-stop result subtype (`error_max_budget_usd`; a summary of https://code.claude.com/docs/en/agent-sdk/typescript lists this subtype but the fetch was truncated) are UNVERIFIED and must be settled by the real-shape fixture, not assumed.

## Decision

### 1. Parser rules (`lib/metrics.py`) — additive, backward compatible

`parse_stream(events) -> Metrics` keeps its signature and the legacy behaviour, and adds real-shape handling:

1. **Legacy shape** (event has no `message` object and no `modelUsage`/`total_cost_usd`): unchanged. Each `assistant|message|tool_use|result` event with top-level `usage` is one dispatch; cost from `usage.cost_usd`; model from top-level `model`. This keeps `test_meta.py` green.
2. **Real shape, assistant events**: model = `message.model`, usage = `message.usage`. Dispatches are counted per DISTINCT `message.id`; when the same `message.id` appears on several events (one API message streamed as several events, Architect F3), keep the LAST usage seen for that id (usage on split events repeats or accumulates; taking the last never double counts). If `message.id` is absent on an event, fall back to counting the event (and the fixture test records that the real stream carries ids or not).
3. **Subagent attribution**: an assistant event with a non-null `parent_tool_use_id` belongs to a subagent. Its model is bucketed like any other model; it counts as a dispatch under its own `message.id`. The primary model is never inferred from these.
4. **Real shape, `result` event** (has `modelUsage` or `total_cost_usd`): it is the authoritative aggregate. It is NOT counted as a dispatch and its `usage` is NOT added on top of per-message usage. `cost_usd` = `total_cost_usd`. Top-level token totals and per-model tokens come from `result.usage` and `result.modelUsage` when present; per-message sums are the fallback when there is no result event. Cross-checks between per-message sums and result totals are recorded by the validator's fixture test as observed facts; equality is NOT asserted a priori (result totals may include subagent tokens the stream omits by default). AC-5.9's `dispatch_count` assertion is "equals the number of distinct `message.id` values in the fixture", not `>= 1`.
5. **Model absence**: an event or bucket with no model is not bucketed as `unknown`; it is reported as absent (a warning) and capture (item 7) fails. `unknown` in any case and the empty string are treated as absent everywhere.
6. **`Metrics` additions** (all with defaults so existing constructors work): `model_primary: str | None` (`system/init` top-level `model`), `models_observed: list[str]`, and a property or field for `tokens.cache_hit_ratio = cache_read / (cache_read + cache_creation + input)`, `0.0` on a zero denominator (FR-5.1). `model_usage` stays a list of `ModelUsage` so `report.py` output and `test_meta.py` keep working.
7. **Capture failure** raises `ModelCaptureError` (new, in `lib/metrics.py`) when: no model string observed; only `unknown`/empty observed; or `system/init` is missing or has no model. The CLI maps it to a non-zero exit (see 4).

### 3. Baseline schema version 2

`SCHEMA_VERSION` in `baseline.py` and `report.py` becomes `"2"`. The baseline is re-captured and never merged (FR-5.6), so there is no compatibility burden. New top-level fields (copied from the per-sample reports, not aggregated as numbers): `model_requested`, `model_resolved` (list), `model_pin_env` (four env vars, null when unset), `effort`, `host_context` (`{"bare": bool, "claude_code_version": str}`), `samples` (`[{"stream_file", "stream_sha256"}]`, 5 entries). `host_context.claude_code_version` is the authoritative CLI version for the baseline; the existing `last_captured_cli_version` stays as the same value for old readers (one source, written twice from one variable). `tokens.cache_hit_ratio` joins `ADVISORY_METRIC_KEYS`. Model keys are flat, `model_usage.<model>.dispatches`, with `classification: "informational"`: they are collected by a new collector in `_collect_metric_values` (per sample, value 0 when a model is absent from that sample), and `_classify` returns `informational` for any key starting `model_usage.`. Nothing splits these keys on `.`; code that needs the model or the suffix uses `removeprefix("model_usage.")` and `rsplit(".", 1)`, because provider-prefixed IDs contain dots and colons (Architect F2).

`model_usage.*` is excluded from per-key threshold comparison (FR-5.7) by construction: it has no `hard_max`, is not in `HARD_METRIC_KEYS`, and `_check_advisory_rules` only walks `ADVISORY_METRIC_KEYS` and `skill_loads.*`. The producer adds an explicit `startswith("model_usage.")` skip and a comment in both check functions so the intent survives a later refactor; AC-5.7(ii) tests it.

### 4. Cost cap, two layers, and budget-stop handling (Architect F6)

**Effort default (revision 1, F4; live docs re-fetched by the reviewer 2026-09-20, https://code.claude.com/docs/en/model-config).** The effort table says `high` is "the default on every model except Opus 4.7" and `xhigh` is "the default on Opus 4.7". So the explicit `--effort xhigh` is redundant on Opus 4.7 and non-default on any other Opus or model. It stays because the smoke baseline must be reproducible whatever the default becomes, and it is recorded in the baseline (`effort`). `xhigh` is therefore documented as a project choice for `opus` only (BINDING-4.3); the documented default is per named version. Revision 3 (loop-3 F13): the live API models overview now lists `Default effort | high` for the latest Opus and Sonnet, and the CLI reference lists `--effort` levels `low, medium, high, xhigh, max, or ultracode`; `xhigh` is therefore non-default for the latest Opus, and the runner still passes it for `opus` only.

Layer 1: the runner passes `--max-budget-usd <cap>` (present in local `claude --help`, CLI 2.1.278). Layer 2: after the run, `_running_cost` reads `total_cost_usd`. Because the CLI checks budget between turns (behaviour UNVERIFIED), a sample can end slightly above the cap; NFR-1 is enforced by the layer-2 post-check. **The runner's in-loop kill is legacy-only (F5).** `runner.py` lines 95 and 252 stop the process when `_running_cost(events) > cost_cap`. On real streams cost appears only on the final `result` event, so during the run `_running_cost` returns 0.0 and the in-loop kill never fires; the new `_running_cost` contract returns `total_cost_usd` only once a `result` exists, which does not restore live enforcement. Real enforcement is layer 1 (the CLI flag) plus the layer-2 post-check. "Two layers" therefore means flag plus post-check for real runs, and in-loop plus post-check only for legacy or fixture streams. The CLI reference describes the flag as "before stopping (print mode only)" and says that at the cap "spawning another subagent fails with `Budget limit reached`"; that is a subagent spawn failure, not a documented result subtype, so the subtype rule below may never match.

A `result` event whose `subtype` is not `success` or whose `is_error` is true is an outcome failure. The exit is 2 (cost-cap), not 4, when ANY of: the subtype contains `budget` (substring; the name `error_max_budget_usd` is UNVERIFIED); the `result` text contains `budget limit` case-insensitively; `is_error` is true and `total_cost_usd >= 0.99 * cap`; or observed cost exceeds the cap. In every such case the sample MUST NOT be passed to `--init-baseline`. Revision 3 (loop-3 F9): today `_init_baseline_flow` aborts only on exit codes 2, 3 and 4, so an outcome-failed sample (exit 1, `outcome.success is False`) would be averaged into the baseline. The producer widens the abort to ANY non-zero exit, including 1; a failed sample is never written to `samples[]` and the flow does not produce a baseline with `sample_status: active`. AC-5.5b gets a case for it. The model-capture failure check must not run on an aborted sample, so a budget stop is never reported as "no model".

### 5. `--init-baseline` and the old baseline

`--init-baseline` runs its 5 samples with the baseline comparison disabled (skip `compare()` and `load_baseline`), and writes a fresh file. It never merges. The per-sample file `.delivery/artifacts/06-development/smoke-streams/sample-<n>.jsonl` is the **full verbatim `stream.jsonl` of that run, scrubbed per section 9** (revision 4, Developer: the earlier "trimmed init only" wording is withdrawn). Reason: the distinctness rule (AC-5.5c: non-overlapping `message.id` sets across the five streams, section 8) needs the assistant and result events, which a four-key init line does not carry. SHA-256 goes in `samples`. The five samples must have distinct `session_id` values, distinct hashes and non-overlapping `message.id` sets (QA W4; a copied stream is rejected by `--init-baseline`; AC-5.5c also checks it independently). Size: a hello-world stream is small (the PRD fixture capture cost $0.041); five streams stay well under 1 MB in total; if a real stream exceeds 500 KB the Plan stage reopens this choice. Regression runs (not init) load with `load_baseline`.

### 6. Producer/validator ordering (BINDING-4.5, FR-4.4)

1. **P0 producer stub commit** (Dispatch-Id A): section 2 signatures and `ModelCaptureError`, `ModelMovedError`, `BaselineSchemaError` classes with legacy-compatible bodies. `test_meta.py` still passes. **A stub is checkable (revision 3, loop-3 F6; rewritten revision 4, QA B1).** Three rules, all machine-checkable with `ast`:
   - **1a. Unchanged-body gate with ONE named exemption.** For every function that exists at `base_sha`, the `ast.dump` of its BODY (signature and decorators excluded) at `validator_start` equals the one at `base_sha`, EXCEPT `report.py::build_report`, which the design requires to gain keys at P0 (section 2 table). This covers `parse_stream`, `_running_cost`, `_spawn_and_tee`, `run_pipeline`, `compare`, `init_baseline`, `_collect_metric_values`, `_classify`, `run_smoke.py` functions, and every other pre-existing function. The exemption list is data in the checker and holds exactly `{build_report}`; adding a name needs a design change.
   - **1b. How the gate still catches a smuggled fix in `build_report`.** The checker transforms the `validator_start` body before comparing: it deletes (i) each dict entry whose key is one of the pinned new keys (`model_requested`, `model_resolved`, `effort`, `host_context`, `session_id`, `stream_file`) and (ii) the single assignment `metrics["tokens.cache_hit_ratio"] = ...`, and it REQUIRES that each deleted value node is a constant literal (`ast.Constant`, or an empty or constant-only `List`/`Dict`, no `Call`, `Name`, `Attribute` or `Subscript` inside). The transformed body must then equal the `base_sha` body. So a P0 `build_report` that computes any new key (reads `events`, calls a helper, parses the stream) fails, and so does any other edit to the function.
   - **1c. New-symbol gate.** New top-level names at P0 are limited to the section 2 names and the three exception classes. New functions return inert values of the pinned type (`check_model_capture` returns `[]`, `check_model_consistency` returns `None`, `load_baseline` returns `json.load` of the file with no schema check) and MUST NOT raise `NotImplementedError` and MUST NOT contain the fix (no reference to `message`, `modelUsage` or `total_cost_usd` string literals in new bodies). Reason for banning `NotImplementedError`: it would make every test that touches a stub fail with a non-assertion type (see the failure-type rule in item 2).
   If 1a to 1c fail, the P0 commit landed part of the fix and the red-first evidence is void.
2. **V validator dispatch** (Dispatch-Id B, `validator_start` = HEAD after P0): writes `tests/test_model_capture.py` and `tests/fixtures/stream_real_shape.jsonl` plus `stream_real_shape.provenance.txt`. Rules for the test file: no module-level import of new names (imports inside test bodies, as `test_meta.py` does), so the file collects against `main`'s unfixed `lib/` for the red run (AC-5.9b needs exit 1, not a collection error, which is exit 2); every `real_shape` assertion message states the defect it detects (`unknown` bucket, `cost_usd 0.0`), so QA W1's "fails for the right reason" is checkable; the conftest guard is respected by patching `lib.baseline._claude_cli_version` and `lib.report._claude_cli_version` where `init_baseline` or `build_report` is called; model strings come from the fixture or synthetic IDs, never literals; test names are the ones in AC-5.2, AC-5.4b, AC-5.5b, AC-5.7, AC-5.9 plus the capture-failure set QA W3 lists. `validator_end` = HEAD when V returns; `lib/` diff between start and end must be empty. **Red-first is measured at `validator_start`, not only at `main` (revision 3, F6).** Against `main`, new tests fail by ImportError or TypeError (new names, new kwargs), which proves nothing about the defect. So besides AC-5.9b (PRD, `main` plus the branch `tests/`), the Plan adds an AC: overlay the validator's `tests/` on `validator_start` (the P0 stub), run `pytest --junitxml=<tmp>/red.xml`, and apply the **failure-type rule (revision 4, QA B1)**:
   - Every `real_shape` and capture-failure test (the AC-5.2, AC-5.4b, AC-5.5b, AC-5.7, AC-5.9 names plus the QA W3 set) is COLLECTED (pytest exit 1, never 2; no `<error>` at collection or setup) and its outcome is FAILED (a `<failure>` element, not `<error>`, not skipped).
   - The failure element's `message` attribute begins with one of exactly two markers: `AssertionError` (a bare or messaged `assert` in the test body) or `Failed: DID NOT RAISE` (a `pytest.raises(...)` block around a stub that returned instead of raising). These are the two outcomes a correct inert stub can produce.
   - A failure whose message begins with `ImportError`, `ModuleNotFoundError`, `SyntaxError`, `TypeError`, `AttributeError`, `NameError` or `NotImplementedError` voids the red evidence. So do collection errors.
   - Test-writing rule for V: capture-failure tests use `pytest.raises(ModelCaptureError, match=...)` (imports inside the test body); value tests use bare `assert` with a message naming the defect. Both produce a permitted marker against an inert stub. A P0 that already contained the fix makes those tests pass at once, and this AC fails.
3. **P1 producer fix commit(s)** (Dispatch-Id A or A2, any producer ID, disjoint from B): implement sections 1, 3, 4, 5. The tests go green.
4. Ordering evidence: the first validator commit is an ancestor of the first P1 commit (`git merge-base --is-ancestor`). This closes QA W1 and is an addition to AC-4.4 for the Plan stage to write. `validator_start` and `validator_end` are SELF-RECORDED by the orchestrator in `s5-separation.txt` (revision 4, QA): the design can prove ORDER only. Derived checks the Plan writes: `validator_start` equals the parent of the first validator commit, and `validator_end` equals the last validator commit; neither proves who authored the commits (item 5).
5. **Accepted limit (revision 1, F9).** The check proves ORDER (validator commit precedes fix commit), not AUTHORSHIP by a different agent: all commits share one git identity, and `Dispatch-Id` trailers and manifests are written by the same orchestrator. Two independent artifacts narrow the gap without closing it: the Dispatch-Id and manifest agent ids are pasted verbatim from the Agent tool result (never typed by hand), and each id has a subagent transcript file in the session directory that the S7 checker may look for (ADR-lmr-005 item 6, layout UNVERIFIED across CLI versions). A determined self-forgery is out of scope for a solo-maintainer repo; the control catches fusion and skipped dispatches, which is what BINDING-5.4 targets.

### 7. Live capture placement

**Run output stays out of the tree (revision 3, loop-3 F2).** `run_smoke.py` defaults `--out-dir` to `delivery-team/tests/smoke/artifacts/` and each run writes `<ts>/stream.jsonl`, `report.json`, `stderr.log` there. The ignore check `check-ignore -v` on `delivery-team/tests/smoke/artifacts/x/stream.jsonl` exits 1 (not ignored; only `*.log` is), so five samples plus the fixture capture would leave untracked files and fail the clean-tree gate (ADR-lmr-005 step 2) after the live capture. Fix, no repo-file change: every S5a and S5b dispatch prompt passes `--out-dir "${TMPDIR:-/tmp}/smoke-out"` (outside the repository; the flag exists, `run_smoke.py` line 57). The only files that enter the tree are the deliberate ones (`smoke-streams/sample-<n>.jsonl`, the baseline, the fixture and its provenance file). The S7 handoff lists this; if a stray run wrote to the default directory, the executor deletes it before step 2, and step 2 catches it if not.

Meta-tests and the fixture cost at most one cheap capture (the PRD's was $0.041). The 5-sample live baseline (about $15, NFR-2) is the expensive step. `state.md` routes it to Stage 7 UAT; see architecture.md section 5 ("Where the live baseline runs") for the sequencing consequence and why doing it last also satisfies Architect F8 (baseline representativeness) by construction.

### 8. Paid-run controls (revision 4, QA W6, DevOps)

Two live-paid steps exist: the fixture capture (S5a) and the five-sample baseline (S5b).

- **Executors.** S5a fixture capture: the V validator dispatch (PRD FR-5.10). S5b baseline capture: a dispatch of role `devops` (in `dod_validators.uat`; the S5b unit lives in `07-uat`, ADR-lmr-005 item 4b). It is a PRODUCER-side executor, not a validator, so it is not listed in the S5b manifest (ADR-lmr-005 item 5 reconciled); the S5b manifest lists the validator (`qa`) that checks AC-5.4, AC-5.5, AC-5.5c and AC-5.6 on the result. The S5b executor's agent id is recorded in the commit trailer `Dispatch-Id` of the baseline commit and must differ from every validator id.
- **Human consent point.** No paid run starts without an explicit operator go, recorded in the S5b (or S5a) dispatch prompt as `operator_go: <date>` copied from the user's message. If the go is absent the dispatch stops and reports.
- **Fixture capture budget.** Every fixture capture command passes `--max-budget-usd 0.25`; at most 2 captures (the PRD's was $0.041). Ceiling $0.50 total.
- **Aggregate S5b ceiling and retry limit.** Per-sample cap stays $3.00 (`--max-budget-usd 3.00`). Aggregate ceiling for the whole S5b unit: $15.00, the NFR-2 envelope, computed as the sum of `total_cost_usd` over EVERY run report in `${TMPDIR:-/tmp}/smoke-out`, aborted runs included (an aborted run with no report counts as its full $3.00 cap). Before starting each run the executor prints `spent=<x> next_cap=3.00` and stops if `spent + 3.00 > 15.00`. Retry limit: at most 2 re-runs of failed samples, so at most 7 runs, whichever limit hits first. A ceiling stop is reported to the operator; raising it needs a new explicit go. Enforcement is procedural (the executor's prompt and log), not a code feature; the layer-2 post-check stays per sample.

### 9. Secret and path scrub of committed captures (revision 4, Security)

Files that enter the tree from live runs: `stream_real_shape.jsonl`, `stream_real_shape.provenance.txt`, `smoke-streams/sample-<n>.jsonl`, the baseline `.json`.
- **Scrub step**, run before commit: replace the operator home directory prefix in every string with `<HOME>` (deterministic text replace; JSON structure and `model`, `message.id`, `session_id`, usage fields are never altered).
- **Scrub AC (Plan writes it, one command over the four file kinds).** The scan finds no match for: `sk-ant-`, `ANTHROPIC_API_KEY`, `Bearer `, `ghp_`, `xox[abp]-`, `arn:aws`, `AKIA`, the current `$HOME` string, `/home/`, `/var/home/`, `/Users/`. A match fails the commit.
- **`model_pin_env` carries no values.** Its four entries are `"set"` or `null` only (section 2 `build_report` row); the baseline never stores an ARN, endpoint or account id.
- **Provenance sidecar is in guard scope.** `stream_real_shape.provenance.txt` is a `.txt`, so `scripts/check_model_pins.py` scans it. It records capture date, CLI version, command line (without env values) and the fixture SHA-256, and MUST NOT carry a resolved model ID or any version-shaped model string: the ID lives only in the `.jsonl`/`.json` files, which are outside the guard. The guard fixture test for the sidecar is the ordinary whole-tree run (AC-1b).

## Alternatives rejected

| Alternative | Why rejected |
|---|---|
| Count every assistant event as a dispatch (as today) | Overstates dispatches and token sums when one message is split across events (F3). |
| Rebuild `cost_usd` and tokens purely from per-message sums | The real stream carries authoritative totals and per-model breakdown on `result`; summing risks double counting and misses subagent tokens. |
| Store `model_usage` as a nested object keyed by model | AC-5.1 asserts keys start with `model_usage.` inside `metrics`; the flat form satisfies the PRD as written. The nested form is safer against dotted IDs but changes the AC; the flat form plus "never split on `.`" removes the risk without changing the PRD. |
| Reject a v1 baseline inside `compare()` | Breaks the existing `test_meta.py` fixtures (`schema_version "1"`) and the 3-test contract. Rejection lives at the load boundary. |
| Keep schema `"1"` | Six top-level fields change meaning; a reader cannot tell an old partial baseline from a new one. |
| `--bare` in the runner | Bare mode authenticates only with `ANTHROPIC_API_KEY` or `apiKeyHelper` (local help; https://code.claude.com/docs/en/headless: "In bare mode, Claude Code never reads OAuth credentials or the system keychain"), so it changes the billing path. That is OQ-12, Michael's call; recommendation: no `--bare`, record `host_context`. New fact from the same page: "`--bare` is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release." A CLI upgrade could therefore flip the default and change what a baseline measures; mitigated by `host_context` and re-recording the fixture on upgrade (risk U9). |
| Validator writes tests after seeing the fix | Violates BINDING-4.5 red-first; ordering in section 6 prevents it. |

## Consequences

- The parser is legacy-compatible (flat events keep working) and real-shape-correct. The cost is a two-mode parser; it is bounded by the fixture tests for both shapes.
- Behaviour that depends on undocumented stream fields (`message.id`, budget subtype, init model field) is pinned by a recorded real fixture and re-verified on a CLI upgrade (R11). Whether real events share `message.id` is the first thing the validator's red phase reveals; if ids are absent the per-event fallback applies and the fixture test records that.
- `--strict-model` is for release runs only; default runs WARN. An `effort moved` WARN mirroring `model moved` is a cheap optional addition (recommended, not required by the PRD).
- A baseline is host-specific unless `--bare` is used; documented, not solved (R13).
- Because the committed v1 baseline is rejected by `load_baseline`, a regression run between S5 and the UAT capture exits 4 with a re-capture message. That is the intended state (BINDING-4.4).
