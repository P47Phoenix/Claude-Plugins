# ADR-001: Single Skill with Agent Sub-Agents vs. Multi-Skill Plugin

## Status

Accepted

## Date

2026-04-01

## Deciders

Celebrimbor (Solution Architect)

## Context

The MTG Commander Deck Builder requires 4 specialized agents (Deck Builder, Rules Judge, Optimization Reviewer, Price Evaluator) plus 1 utility (Card Finder). The original idea brief proposed an `agents/` directory with agent definition files (e.g., `agents/deck-builder.md`, `agents/rules-judge.md`).

However, examining the existing Claude-Plugins repository reveals that **no existing plugin uses agent definition files**. The delivery-team plugin -- the most complex plugin in the repo with 11 skills -- uses the `Agent` tool to spawn sub-agents with inline prompt templates. The architect skill, developer skill, and delivery-flow orchestrator all follow this same pattern:

1. SKILL.md detects the task type
2. SKILL.md reads the relevant reference file(s) via the `Read` tool
3. SKILL.md spawns a sub-agent using the `Agent` tool, passing reference contents in the prompt
4. The sub-agent executes with isolated context and returns its output

There is no `agents/` directory convention in this repo. Agent "definitions" are prompt templates embedded in SKILL.md.

**Two structural alternatives exist:**

**Option A: Single SKILL.md orchestrator with 4 sub-agents** (inline agent definitions)
- SKILL.md contains prompt templates for all 4 agents
- Sub-agents are spawned via `Agent` tool in sequence
- Follows the existing delivery-flow pattern exactly

**Option B: Multi-skill plugin with 4 independent skills + 1 orchestrator**
- Each agent becomes its own skill in `skills/deck-builder/SKILL.md`, `skills/rules-judge/SKILL.md`, etc.
- An orchestrator skill sequences them
- Each skill could be invoked independently

## Decision

**Option A: Single SKILL.md orchestrator with 4 sub-agents.**

The 4 agents are pipeline stages, not independently useful capabilities. A user would never invoke the Rules Judge in isolation (what deck would it validate?). The Optimization Reviewer without a Deck Builder output is meaningless. These agents have value only as a pipeline -- they are not skills.

The multi-skill pattern is appropriate when each skill is independently invocable (e.g., the delivery-team's architect and developer skills). The deck builder agents are pipeline stages with strict input/output contracts between them.

Additionally, the `agents/` directory pattern from the idea brief does not exist in this codebase. Introducing a new convention for a single plugin adds cognitive overhead for contributors who are familiar with the existing patterns.

## Consequences

**Easier:**
- Plugin structure is simple: one SKILL.md, references/, scripts/. No new directories.
- Follows established patterns. Contributors familiar with delivery-team know exactly how this works.
- Agent prompt templates are co-located in the orchestrator, making the pipeline flow readable in one file.
- No need to register multiple skills in marketplace.json.

**Harder:**
- SKILL.md will be large (estimated 400-600 lines with 4 agent prompt templates + orchestration logic). This is comparable to delivery-flow's SKILL.md, which is the precedent.
- Modifying a single agent's behavior requires editing SKILL.md rather than an isolated file. Mitigated by clear section headers and the fact that agent behavior is primarily driven by reference files, not the prompt templates.
- If a future version needs agents to be independently invocable (e.g., "just run the Rules Judge on this existing deck"), refactoring to multi-skill would be needed. This is acceptable because v1 explicitly scopes to new builds only.
