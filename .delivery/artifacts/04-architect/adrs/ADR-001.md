# ADR-001: Bash+Python Invocation Model for Rule Evaluation

**Status**: Proposed
**Date**: 2026-03-28
**Author**: Celebrimbor, Solution Architect
**Traces To**: PRD US-12, FR-11, NFR-02

---

## Context

The delivery-flow pipeline orchestrator runs as a SKILL.md prompt interpreted by Claude. When the orchestrator needs to make a flow-control decision (stage routing, DoD gate evaluation, escalation), it currently interprets prose criteria inline. This produces non-deterministic results because the same prose is interpreted differently across runs.

The rules engine must evaluate conditions deterministically. Two approaches exist:

1. **Inline evaluation**: Embed the rule evaluation logic as structured instructions in SKILL.md. The orchestrator reads the rules and evaluates conditions within the conversation context.

2. **Bash+Python invocation**: The orchestrator writes context to a JSON file, invokes a Python script via the Bash tool, and reads the decision from stdout.

## Decision

We adopt the **Bash+Python invocation model**.

The orchestrator serializes pipeline state to a JSON file, invokes `evaluate_rules.py` via a Bash tool call, and parses the JSON result from stdout.

## Rationale

### Why not inline evaluation?

**Non-determinism is the problem we are solving.** Inline evaluation means the AI interprets condition logic (e.g., "if project type is BUG_FIX and risk tolerance is standard, then architect stage depth is light"). Even with structured rules in the prompt, the AI may:
- Misparse nested conditions (AND/OR precedence)
- Apply conditions in inconsistent order
- Silently skip conditions when context is long
- Produce different results when the same rule is evaluated at different points in a conversation

These are not theoretical risks. They are the documented failure modes that motivated this feature (PRD Section 1).

**Code-executed evaluation eliminates this class of failure.** Python evaluates `condition["AND"][0]["field"] == "project.type"` the same way every time. There is no interpretation variance.

### Why Bash tool specifically?

The orchestrator operates in a Claude Code session where the Bash tool is the sanctioned mechanism for executing code. The alternatives are:

| Approach | Why rejected |
|----------|-------------|
| MCP server | Adds infrastructure complexity. The rules engine has no need for persistent connections or streaming. A stateless invocation is simpler and sufficient. |
| Inline Python (via prompt) | The orchestrator is an AI prompt, not a code execution environment. "Evaluating Python in the prompt" is still prompt interpretation -- just with Python-like syntax. |
| Write to file, read back | This IS the Bash+Python model. Writing JSON, invoking Python, reading JSON is the most explicit and auditable version. |

### Trade-offs accepted

| Trade-off | Accepted because |
|-----------|-----------------|
| Each evaluation requires a Bash tool call (latency) | Evaluation is sub-500ms (NFR-01). One Bash call per decision point (5-15 per pipeline run) adds 2.5-7.5 seconds total. Acceptable for determinism. |
| Context must be serialized to JSON | Context serialization is a feature, not a cost. It forces explicit documentation of what data influences each decision. The serialized context is the audit trail input. |
| Two formats (YAML config vs JSON rules) | Users work in YAML (familiar). Engine works in JSON (type-safe). Translation layer handles the boundary. Users never see JSON. |

## Consequences

- The orchestrator MUST write context to `.delivery/tmp/` before every decision point.
- The orchestrator MUST parse JSON output after every evaluation.
- Rule evaluation is fully testable outside the pipeline (invoke the script directly with test context).
- The `--dry-run` flag provides free preview capability (no pipeline needed).
- CI/CD integration becomes possible (invoke the same script from GitHub Actions).
- Audit trail is a natural byproduct (the script writes JSONL as a side effect).

## Alternatives Considered

### A1: Inline SKILL.md Evaluation Tables

Embed routing tables directly in SKILL.md as markdown tables. The orchestrator reads the table and looks up the correct routing.

**Rejected because**: Even with structured tables, the AI's table parsing is not 100% reliable for 126-cell routing tables (6 types x 7 stages x 3 risks). More critically, DoD gate evaluation requires weighted scoring and threshold comparison -- operations that are trivially correct in code but error-prone in prompt interpretation.

### A2: Hybrid Model (Simple Inline, Complex External)

Route simple decisions (routing lookups) inline and complex decisions (gate scoring) to external Python.

**Rejected because**: This creates two code paths for the same category of decision (flow control). Debugging requires knowing which path was taken. The simplicity gain from inline routing is offset by the complexity of maintaining two evaluation strategies. One strategy, consistently applied, is simpler to maintain and audit.
