# ADR-001: Plugin Structure -- Mirror delivery-team vs Custom Layout

**Status:** Accepted
**Date:** 2026-04-12
**Deciders:** Solution Architect (Celebrimbor)
**Pipeline:** run-2026-04-12-hw01 | **Type:** GREENFIELD

---

> "The pattern of the delivery-team plugin has proven its worth through many seasons of use. To deviate from a proven forge technique without cause is folly -- but to follow it blindly is equally unwise. We choose the path of informed mirroring."

---

## Context

The hardware-team plugin needs a directory structure that:

1. Follows CLAUDE.md conventions (SKILL.md, skills/, references/, hooks/, scripts/)
2. Supports 7 skills (1 orchestrator + 6 roles) with context isolation
3. Accommodates hooks, shared scripts, and test fixtures
4. Is discoverable by the Claude Code plugin harness via marketplace.json
5. Allows future extension (Phase 2 roles, new stages)

The delivery-team plugin provides a proven reference implementation with 11 skills, hooks, scripts, and a mature marketplace.json structure. The question is whether to mirror it closely or design a custom structure.

## Decision

**Mirror the delivery-team plugin structure** with hardware-specific adaptations:

```
hardware-team/
├── SKILL.md                    # Plugin entrypoint (same as delivery-team)
├── LICENSE.txt                 # Same license structure
├── hooks/                      # Same hook infrastructure
│   ├── hooks.json
│   └── *.py
├── scripts/                    # Shared utilities (same pattern)
├── skills/                     # One directory per skill (same pattern)
│   ├── hardware-flow/          # Orchestrator (mirrors delivery-flow)
│   │   ├── SKILL.md
│   │   ├── references/
│   │   └── scripts/
│   ├── hw-product-owner/       # Role skill (mirrors product-delivery)
│   │   ├── SKILL.md
│   │   └── references/
│   └── ... (6 more role skills)
└── references/                 # Plugin-level shared resources
    ├── test-fixtures/          # Hardware-specific addition
    └── prerequisites.md
```

**Hardware-specific adaptations** (deviations from delivery-team):

1. **Test fixtures directory** (`references/test-fixtures/`): delivery-team has `references/fixtures/` for config schema fixtures; hardware-team adds a full reference KiCad project with seeded defects for gate validation
2. **Prerequisites documentation** (`references/prerequisites.md`): Documents the kicad-happy external dependency with installation instructions -- delivery-team has no equivalent external plugin dependency
3. **No CROSS-SKILL-REFERENCES.md**: delivery-team uses this for cross-skill reference sharing; hardware-team skills do not share references (each role is fully isolated)
4. **Orchestrator scripts**: `hardware-flow/scripts/validate_config.py` mirrors delivery-flow's config validation pattern

## Consequences

### What becomes easier

- **Developer familiarity**: Anyone who has worked with delivery-team immediately understands the structure
- **Tooling compatibility**: `plugin-dev:plugin-validator` works out of the box
- **Documentation**: CLAUDE.md conventions are already documented; no new patterns to explain
- **Future plugins**: Establishes the structure as a reliable template for additional delivery-style plugins

### What becomes harder

- **Nothing significant**: The mirrored structure does not impose constraints that conflict with hardware-specific needs
- **Minor overhead**: Some directories (e.g., `scripts/` at plugin level) may be sparse in Phase 1 but exist for future use

## Reversibility

**Two-way door.** This decision is reversible at moderate cost. The plugin directory structure can be reorganized by:

1. Moving skill directories to their new locations
2. Updating `marketplace.json` skill paths to reflect the new layout
3. Updating any cross-references in SKILL.md files

No external consumers depend on the internal directory structure -- only `marketplace.json` exposes skill paths to the Claude Code harness. The cost of reversal is a single refactoring commit affecting directory layout and marketplace registration. No runtime behavior changes.

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|---|---|---|---|
| Flat structure (all skills at top level) | Simpler directory tree | Breaks CLAUDE.md conventions; no separation of orchestrator from roles; plugin-validator would fail | Violates established patterns |
| Nested role groups (skills/design/ee, skills/design/pcb-layout) | Logical grouping by hardware phase | Adds unnecessary nesting; not how delivery-team organizes skills; complicates skill paths in marketplace.json | Over-engineering with no benefit |
| Shared references directory (all role references in one place) | Fewer directories | Breaks context isolation principle; roles would need to filter relevant references | Violates NFR-002 (context isolation) |
