# ADR-lmr-005: Dispatch-manifest shape (OQ-4) and the ship gate

- **Status**: Proposed (flips to Accepted when Stage 4 DoD passes)
- **Date**: 2026-09-20
- **Run**: run-2026-05-28-o48m, BACKLOG-108
- **Owner**: Solution Architect (PRD FR-7.3, FR-7.4, AC-DISP, OQ-4; BINDING-5.1, BINDING-5.4; Architect DoD round-2 F5, F8; QA W5)

## Context

AC-DISP (PRD FR-7.4) enforces "One Role = One Sub-Agent" with one file per stage, `<stage>/dispatch-manifest.txt`: line 1 `expected_validators: N`, then `<role><TAB><agent-id>` per dispatch; N must equal the line count, roles distinct, agent ids distinct. Its `REQUIRED` stage list is the PRD's guess (`02-refine`, `04-architect`, `05-plan`, `06-development`) and the PRD invites the Architect to correct it (OQ-4). The PRD also asks where the `dod_validators` counts live.

Evidence gathered in this stage (commands and files read):
- `.delivery/config.yml` lines 56 to 63 hold the source of truth: `idea: [po, architect]`, `refine: [po, architect, developer, qa]`, `design: [ux, po, qa, developer, architect]`, `architect: [architect, qa, developer, devops, security]`, `plan: [sm, po, qa, developer, devops]`, `development: [developer, qa, architect, tech-writer]`, `uat: [qa, devops, po, tech-writer]`.
- `.delivery/state.md`: `stages_completed: [1, 2]`, `stages_skipped: [3]`, routing `idea: light, refine: light, design: skip, architect: light, plan: light, development: full, uat: full`.
- `delivery-flow/SKILL.md` (Depth Definitions, read): Light = "Primary agent only, blocking criteria only, reduced DoD (primary + 1 reviewer)". Yet Stage 2 in this run, routed light, ran four validators (`.delivery/artifacts/02-refine/dod/` holds po, architect, developer, qa reviews). So N for a light stage is "validators actually dispatched", bounded by the config list, not equal to it.
- Stage directory names: `delivery-flow/references/pipeline-stages.md` line 550 writes to `artifacts/06-dev`; this run's PRD ACs and `.delivery/artifacts/` use `06-development`; both directories exist, and `06-development/dod/` already holds files from earlier waves (`S1-S2-architect-review.md`, `S3-architect-review.md`, and others). Stage 7 uses `07-uat`.
- DoD rounds and per-story units: `02-refine/dod/` and `04-architect/dod/` hold `-r2` files (a role re-validates in a second round); `06-development/dod/` holds per-story groups (`S1-S2-*`, `S3-*`). The PRD format (roles distinct within one manifest) cannot describe a second round by the same role, nor seven stories.

## Decision

1. **REQUIRED stage directories** for AC-DISP in this run (revision 3, loop-3 F5): `04-architect`, `05-plan`, `06-development`, `07-uat`. Excluded with reason: `01-idea` and `02-refine` (both completed before the manifest rule existed; no artifact recorded the Stage 2 dispatch ids, and item 6 forbids typing ids, so a Stage 2 manifest could only be invented; `find .delivery -name 'dispatch-manifest*'` prints nothing today), `03-design` (skipped, `stages_skipped: [3]`). The PRD lists `02-refine` in REQUIRED, so dropping it is a flagged PRD deviation (P22, owner PO); the alternative, a reconstructed manifest exempt from the transcript check, would make AC-DISP pass on typed ids and is rejected. `04-architect` stays REQUIRED but part of it was dispatched before the manifest writer existed: those rounds use the RECOVERED form of item 4a, which is only valid when every id has a transcript file. `07-uat` is added because UAT is routed `full`, has its own `dod_validators.uat`, and (per architecture.md section 5) ship happens after UAT passes. If the Plan stage instead ships before UAT, drop `07-uat` from the list and say so in the plan; the checker takes the list as data.
2. **Stage-to-config-key map** (revision 4, Architect: `02-refine` removed, item 1 dropped it from REQUIRED): `04-architect` to `architect`, `05-plan` to `plan`, `06-development` to `development`, `07-uat` to `uat`. The checker reads the list with a stdlib regex on `.delivery/config.yml` lines of the form `  <key>: [a, b, c]` (no YAML dependency, per BC-03).
3. **The development directory is `06-development` for this run.** The PRD ACs (AC-3.1 ledger, AC-4.4 `s5-separation.txt`, `smoke-streams/`) already hard-code it. The orchestrator's default of `06-dev` (pipeline-stages.md) is a reference-doc mismatch to log for a later wave; the Stage 6 dispatch prompts must state `06-development` explicitly. Stale earlier-wave files in `06-development/dod/` are not read by the checker (it reads only `dispatch-manifest*.txt`).
4. **Manifest = one DoD round of one unit.** File naming: the stage-level round is `dispatch-manifest.txt`; extra rounds and per-story units are `dispatch-manifest-<label>.txt` (`-r2`, `-S1`, `-S2`, and so on). The format inside stays exactly as the PRD wrote it.
   4a. **Recovered form (revision 3, F5).** For dispatches made before the writer existed (Stage 4 rounds 1 to 3 of this run), the manifest may add a second line `# provenance: transcript-recovered`. Lines starting `#` are not counted in `N`. The checker then REQUIRES a transcript file `subagents/agent-<id>.jsonl` for every id in that manifest and FAILS (no skip note) when one is missing; ids come from those file names, not from memory. A manifest without the provenance line keeps the item 6 rule (ids pasted from the Agent tool result; transcript check is a supporting check). This stops a placeholder id from passing.
   4b. **Units and directories (revision 3, F4).** The real story units are S1, S2, S3, S4, S5a, S5b, S6, S7 and S7b (S5 is split, architecture.md section 5). Directory per unit: S1, S2, S3, S4, S5a, S6 in `06-development`; S5b (live capture, Stage 7), S7 and S7b in `07-uat` (S7 executes after UAT, so its manifest cannot live under `06-development`). The required-name set is data in the checker: `06-development` requires S1, S2, S3, S4, S5a, S6; `07-uat` requires S5b and S7 before the push and S7b after it. Each manifest covers only the validators of that unit's deliverables.
5. **Checker rules** (extends the PRD script, same negative self-test approach): for each required stage the checker requires at least one `dispatch-manifest*.txt` (a stage with none is a violation, so absence cannot pass, as in the PRD); for `06-development` and `07-uat` it requires the per-unit manifests named in item 4b (`dispatch-manifest-<unit>.txt`). **Producer and executor dispatches are NOT listed in any manifest (revision 4, QA W5; reconciles item 6)**: a manifest lists validators only. Producer and executor ids are recorded solely in `Dispatch-Id` commit trailers; each manifest passes the PRD's four checks (line 1 shape, `N == lines`, roles distinct, agent ids distinct) plus two more: every role is in the config list for that stage and `N <=` the list length (BINDING-5.4: never more dispatches than the list); and every agent id is unique across ALL manifests of the run (a reused agent across rounds is a fusion or a copy). **Stage cap (revision 4, QA W7).** The shipped prose says `dod_validators.<stage>` is the cap "per DoD checkpoint" (S2 block 2 wording, architecture.md section 4), not per stage in total: one stage runs several checkpoints (rounds, units), each at most the list length. The checker enforces the checkpoint bound (`N <=` list length per manifest, above). It does NOT enforce a per-stage total, because per-unit manifests legitimately multiply (for example `07-uat` holds S5b, S7 and S7b). The S2 block 2 wording "at most that many subagents per stage" is therefore replaced by "at most that many per DoD checkpoint" in architecture.md section 4 S2 (Revision 4 changelog); this is a design text fix, no PRD requirement changes.
6. **Cross-check for authorship claims (QA W5)**: the AC-4.4 `Dispatch-Id` trailers in the S5 commits must each appear in the `06-development` manifest set (the validator id must appear in the S5a manifest under the `qa` role; producer ids are NOT in any manifest, so the cross-check for them is that the producer trailer id set is disjoint from every manifest id and from the validator trailer set; revision 4, QA W5), and `run_smoke.py` joins `lib/` in the producer path list so one commit cannot touch it together with the validator files. These are additions for the Plan stage to write as AC text. **Agent ids are copied, not typed (F9).** The `<agent-id>` column and every `Dispatch-Id` value are the id string from the Agent tool result, pasted verbatim. Independent artifact: Claude Code writes one transcript per subagent under the session directory, observed here at `~/.claude/projects/<project-slug>/<session-id>/subagents/agent-<id>.jsonl` (with a `.meta.json`), e.g. `agent-a224da00ed12ff520.jsonl` (listed by `ls` this stage). The checker asserts that a transcript file exists for each manifest id. **Skip rule (revision 4, QA W4, Security):** the check is skipped only when the project's session directory tree (`~/.claude/projects/<project-slug>/`) does not exist at all, and the skip is printed loudly (`TRANSCRIPT_CHECK=SKIPPED reason=<...>`), never silently. When the tree exists, an id with no `agent-<id>.jsonl` in ANY session directory of that slug (rounds may span sessions) FAILS the check. S7b (item 8) always runs the transcript check and prints `TRANSCRIPT_CHECK=RAN` or the loud skip line. The path layout is observed on this CLI only (UNVERIFIED for other versions). The check proves a file exists for the id, not that the transcript matches the role or unit; that stays an accepted limit. Even so, the orchestrator writes the manifests, so this remains an accepted limit (ADR-lmr-004 section 6).
7. **Base ref for pre-ship ACs** (Architect F8): the S1 developer records `base_sha=$(git merge-base main HEAD)` once, in `.delivery/artifacts/06-development/base-sha.txt`. AC-2.1, AC-2.5, AC-4.4 and AC-5.9b, which use the moving `main` ref, are evaluated against that SHA. If `main` has not advanced the result is identical; if it has, the line numbers named in AC-2.1 and the diff in AC-2.5 stay meaningful. The named source lines in AC-2.1 are properties of the base commit, not of whatever `main` is at ship time.
8. **Ship gate** (S7; revision 1 rewrites this item for adversarial findings F2 and F3). The gate has TWO blocks (revision 3, loop-3 F3). **Block A (pre-squash)** is step 0 and runs on the feature branch head, BEFORE the squash-rebase, because AC-4.4 needs the per-commit `Dispatch-Id` trailers and `git merge-base --is-ancestor first-validator first-fix`, which a squash destroys (PRD FR-7.3: pre-ship ACs "stop being meaningful after the ff-merge"; FR-4.4). It evaluates the branch tip commit `PRE_SHA`, recorded in the log. **Block B (post-squash)** is steps 1 to 9. It runs after the FINAL commit (CHANGELOG, memory topic, every rework edit) and after the squash-rebase and ff-merge, immediately before `git push`, and evaluates `SHIP_SHA`, the single squashed commit. The path stays squash-rebase, ff-merge, push, with no PR. Any non-zero exit stops the ship.
   **Ship checkout (revision 3, loop-3 F1).** Block B runs in the MAIN checkout (the one holding `main`, so the ff-merge and the push happen there), not in the feature worktree, where `main` cannot also be checked out. The main checkout holds nested worktrees under `.claude/worktrees/`, and `.gitignore` has no entry for them, so a plain `git status --porcelain --untracked-files=all` prints `?? .claude/worktrees/w1/`. Reproduced this revision in a scratch repo with one nested worktree: raw status printed `?? .claude/worktrees/w1/`; with the pathspec `-- . ':!.claude/worktrees'` it printed nothing, and a real stray file `b` still printed `?? b`. So step 2 and the pre-push hook (ADR-lmr-002 D8) both use that pathspec; no `.gitignore` edit is made (the ignore file is a repo-file change outside the S1 scope and the guard already skips nested worktrees as non-files). Plan AC: step 2 exits 0 in the main checkout with at least one nested worktree present, and exits non-zero when a stray untracked file is added.
   **Block A step 0.** Pre-ship-only ACs (AC-2.1, AC-2.5, AC-4.4, AC-5.9b), evaluated against `base-sha.txt` (item 7) on the branch tip, BEFORE the squash-rebase. Its output is teed to the same out-of-tree log as Block B (the log is opened at step 0). Step 0 also runs the guard canary (ADR-lmr-002 D9) in a `mktemp -d` copy (revision 5, QA W2), and prints its result.
   Block B steps:
   1. `git fetch origin main`, then `test "$(git rev-list --count HEAD..origin/main)" = 0` (not behind; revision 3, F11: the bare count always exits 0, so it is wrapped in `test`). If not, rebase and restart at step 0.
   2. **Clean tree (F2).** `test -z "$(git status --porcelain --untracked-files=all -- . ':!.claude/worktrees')"` succeeds, and `! git ls-files -v | grep -q '^[a-zS]'` succeeds (no assume-unchanged or skip-worktree flags that would hide edits). Revision 2 (loop-2 F1): the first draft used `git ls-files -v | grep -c '^[a-zS]'` and required it to print `0`, but `grep -c` exits 1 when the count is 0, which is the CLEAN case, so an exit-driven executor would stop the ship on a healthy tree. Executed this revision: the `grep -c` form printed `0` with `exit=1`. Rule for the whole gate: a step is judged by its exit status, and a step that reports a count also prints the value into the S7 log (`step=<n> exit=<rc> value=<v>`), so the log records printed values, not only codes. With both true, the guard scope (`git ls-files --cached --others --exclude-standard`) equals the HEAD tree and file bytes equal the committed bytes, so a scan of the working tree IS a scan of the commit that is pushed. Before this fix, an unstaged edit or an untracked file could make the scan and the push disagree. Run for real in this stage: on the design worktree the porcelain check printed `?? .delivery/artifacts/04-architect/challenger/loop-1.md` (dirty, would stop the ship), and the flag check found no flagged file (see the exit-status note above).
   3. `SHIP_SHA=$(git rev-parse HEAD)`, recorded in the log.
   4. `python3 scripts/check_model_pins.py` strict: `guard-scope hits 0 files 0`, `exit=0`. The step is judged on the guard's OWN return code, captured as `rc=$?` and printed (`step=4 exit=<rc>`); a crashed or missing script (rc 2, 127, or stdout without a `guard-scope hits` line) FAILS the step (revision 4, QA W1). The guard-canary AC (ADR-lmr-002 D9, revision 4) runs in Block A step 0 and again in S7b.
   5. `test "$canonical_count" = "$script_list_count"` (R12 equivalence; both values printed into the log; revision 3, F11). **Extraction (revision 4, Developer):** `canonical_count` is field 3 of the LAST line of the PRD section 1 canonical command (`guard-scope hits <N> files <M>`; `tail -n 1 | awk '{print $3}'`); `script_list_count` is the number of hit lines printed by `python3 scripts/check_model_pins.py --list` (lines starting `pin `, `stamp ` or `prose `, counted with `awk '/^(pin|stamp|prose) /{n++} END{print n+0}'`, which prints `0` and exits 0 on a clean tree, unlike `grep -c`). Each value must also equal the `hits` field of the guard's own summary line, both commands must have exited 0 or 1, and an empty value fails the step.
   6. `python3 scripts/check_skill_budgets.py` exit 0. This step is the only line-budget control on the ship path unless the push trigger below is adopted (F3): `skill-line-budget.yml` is `on: pull_request` only (`sed -n 1,8p` prints `pull_request:` and the two `paths:`), so a direct push never runs it.
   7. AC-6.1 prints `MATCH` (ADR-lmr-001), plus the telemetry-hash record required by ADR-lmr-001 decision 7.
   8. AC-DISP over the required-name set of item 4b MINUS S7b (revision 3, F4). The S7 manifest covers only S7's pre-ship deliverables (CHANGELOG entry, memory topic); the ship log itself, which contains this step, is validated by S7b, so there is no circularity. S7b's own manifest is checked after the push: the orchestrator re-runs AC-DISP with S7b included in the post-ship docs commit and pastes the output.
   9. **Operator go and aggregate spend check (revision 4, DevOps).** The push needs an explicit operator go in the S7 prompt (`operator_go: <date>`), in addition to the paid-run go in ADR-lmr-004 section 8. **Order (revision 5, QA W5):** the spend check runs (a) before each S5b run and (b) once in Block B as step 1a, before the fetch at step 1, using the extraction snippet of ADR-lmr-004 section 8; it reads the tracked `07-uat/s5b-spend.txt` and the durable `$SMOKE_OUT`, and a missing or non-numeric cost FAILS it. It requires `spent <= 15.00` and prints `spent=<x>` into the log. Step 9 itself is only: operator go check, then `git push origin main`; then `test "$(git rev-list --count origin/main..HEAD)" = 0` (revision 3, F11: it was a bare count that always exited 0). Reproduced: `git rev-list --count HEAD~1..HEAD` printed `1` with rc 0, and the `test "$(...)" = 0` form returned rc 1.
   **Objective evidence (F3).** Step 0 and steps 1 to 8 run as ONE teed sequence under `set -o pipefail` (step 0 first, then the squash, then steps 1 to 8), teed to a log OUTSIDE the repository (`${TMPDIR:-/tmp}/ship-gate-<first 12 of SHIP_SHA>.log`; a log inside the tree would dirty it and invalidate step 2). Each step prints `step=<n> exit=<rc>` from the shell, and the block prints `SHIP_GATE=PASS sha=<SHIP_SHA>` only when every exit was 0. The S7 report cites the log path and its `sha256sum` and pastes it verbatim; a hand-typed summary is not accepted. The same executor still authors it, so the log is necessary but not sufficient; the independent check below is what makes it objective.
   **Independent post-push verification, S7b (F3).** After the push, a DIFFERENT dispatch (role `devops`, which is in `dod_validators.uat`; agent id copied from the Agent tool result, see item 6) creates a fresh clone of `origin/main` (`git clone --no-hardlinks <origin> <tmpdir>`), asserts `git rev-parse HEAD` equals the `SHIP_SHA` in the S7 log, and re-runs steps 4, 5, 6 and 7 and the guard canary there, returning the raw output. Its one-line manifest is `07-uat/dispatch-manifest-S7b.txt` (item 4 naming; the roles-distinct and ids-unique rules of item 5 still hold). Its report is written to `.delivery/artifacts/07-uat/ship-verification.txt` and lands in the normal post-ship state commit (docs only; `.delivery/` is outside the guard scope and no SKILL.md is touched). Procedure proven in this stage on a clone of the design worktree HEAD (`85db40f`): the clone's `git status --porcelain` printed 0 lines, the untracked challenger file was absent (a clone holds only committed bytes), `check_skill_budgets.py` printed `BUDGET CHECK PASSED: 17 file(s) checked, 0 known-debt, 0 exception(s).`, and the hash check printed `MATCH`. If S7b fails, the remedy is a fix-forward commit that goes through the whole gate again; main is never force-pushed or rewritten (irreversible; needs an explicit user decision).
   **S1 to S4 leave the guard red until S4 (revision 4, DevOps; carries P14).** Between the S1 and S4 commits the tree still contains pins, so the guard workflow would fail on any of those commits if pushed. The single squashed push means `main` sees only the final green commit. S1 to S3 are never pushed to `main` on their own; a branch push is harmless (the workflow's `push` trigger is `main` only).
   **S7b transcript check (revision 4, Security).** S7b always runs the item 6 transcript check over all manifests, prints `TRANSCRIPT_CHECK=RAN` or the loud skip line, and a skipped check is reported in `ship-verification.txt`, never omitted. **Layout drift (revision 5, QA W4):** the transcript directory layout is OBSERVED on CLI 2.1.278 only, not documented. The checker must tolerate a different layout: if it cannot locate a transcript for an id it prints `TRANSCRIPT_CHECK=SKIPPED layout-drift <id>` and reports it; it never reports `RAN` on a layout it did not find, and drift never fails the ship on its own.
   **Workflow and shell hygiene (revision 4, Security).** Any workflow this design adds or edits (`stale-model-id-guard.yml`, and the new `push` trigger on `skill-line-budget.yml`) declares `permissions: contents: read` at workflow level and uses `actions/checkout` with `persist-credentials: false`. Temp paths in the gate, S7b and dispatch prompts come from `mktemp -d` (never fixed names under `/tmp`). Shell steps that pass file lists use NUL delimiters (`-z` output, `xargs -0`), as the pre-commit reference in ADR-lmr-002 D8 already does; the pre-push hook follows the same rule.
   **Hook installation is not implied (revision 3, loop-3 F14).** In this repository `git config --show-origin core.hooksPath` printed `file:/var/home/meconnelly/Documents/GitHub/Claude-Plugins/.git/config  /var/home/meconnelly/Documents/GitHub/Claude-Plugins/.git/hooks`, a directory holding only `*.sample` files, so neither the existing pre-commit hook nor the new pre-push hook runs here until the operator runs `git config core.hooksPath .githooks`. The S1 and S7 handoffs (architecture.md section 12) require that command and a log line `hooksPath=<value>`; until it is set the pre-push hook is INERT and steps 0 to 8 plus S7b are the only controls.
   **Pre-push hook (F3, now designed into S1, not left to PO confirmation).** ADR-lmr-002 D8 specifies `.githooks/pre-push`, which for a push to `refs/heads/main` requires the pushed sha to equal `HEAD`, a clean tree (same `.claude/worktrees` pathspec as step 2), and strict runs of the guard and the budget checker. It is opt-in via `core.hooksPath` and `git push --no-verify` skips it, so it is defence in depth; the S7b check is what does not rely on the pusher.
   **Budget push trigger (PRD addition, PO confirms at Plan).** Add `push: branches: [main]` with the existing `paths:` filter to `.github/workflows/skill-line-budget.yml` (edit through `plugin-dev:hook-development`, FR-1.4 route). Verified: the checker reads `PR_BODY` with a default of empty (`os.environ.get("PR_BODY", "")`) and `env -u PR_BODY python3 scripts/check_skill_budgets.py` printed `BUDGET CHECK PASSED: 17 file(s) ...` (exit 0), so the job runs on push; it also means no `Budget-Exception:` can be granted on a push (that token lives in the PR body). **What applies instead (revision 4, DevOps):** on this ship path a budget overrun has no exception route; the S3 owner fixes the line count (all 25 files are proved zero-delta, ADR-lmr-003), and a real exception would need a `known_debt[]` entry with `target_wave:` in `governance/skill-budgets.json` committed BEFORE the ship (a tracked edit that steps 6 and S7b see), never a PR-body token. 0 exceptions are needed today. The existing `env:` use of `github.event.pull_request.body` is not inside `run:`, so `workflow-injection-lint.yml` stays green. If the PO declines: line budgets are NOT enforced by CI on direct pushes to main, and steps 6 and S7b are the only controls; state that in the plan.
   **Detect, not prevent (Revision 2, loop-2 F2; ACCEPTED RESIDUAL RISK).** With a direct push to `main` and no PR (BINDING-5.1), nothing in this design PREVENTS a pin from reaching `main` if the pusher skips the gate. The local pre-push hook is opt-in (`core.hooksPath`) and `git push --no-verify` skips it. The step 0 to 8 gate is run by the same orchestrator that pushes, and its log is a self-produced text file. The two controls the pusher does not run, S7b and the `push: main` guard workflow (ADR-lmr-002 D7), both fire AFTER `git push origin main`. So the design is detection with fix-forward for a careless or hostile pusher; the gate is an honest-pusher control, not an access control. The threat model this run addresses is accidental drift, not an adversary.
   - **Residual risk RR-1**: a pin, or a budget breach, can land on `main` and stay there until S7b or CI notices. Blast radius: one bad commit on main, no runtime consumer (no service, static text and a local harness). Remedy: a fix-forward commit through the whole gate (main is never force-pushed).
   - **Prevention that would close it**: GitHub branch protection on `main` with required status checks (`stale-model-id-guard`, `skill-line-budget`) and no direct pushes, or a server-side `pre-receive` hook. Both conflict with the no-PR ship path as decided, so neither is designed in; adopting one changes BINDING-5.1 and is a product decision.
   - **Owner**: the PO (Michael Connelly, repository owner), who owns BINDING-5.1 and the repository settings.
   - **Revisit trigger**: any one of (a) S7b or the push workflow fails after a ship (a pin actually reached main), (b) a second contributor gains push rights to `main`, (c) the PO revisits BINDING-5.1 (for example adopts a PR-based ship). Any trigger reopens this ADR with branch protection as the first option.
9. **SKILL.md edits after the baseline capture** invalidate what the baseline measured (Architect F8). By design the live capture is the LAST step before ship (architecture.md section 5), so no such edit is expected; if DoD rework touches a SKILL.md after the capture, either re-capture or record an explicit waiver in the S7 report.

## Alternatives rejected

| Alternative | Why rejected |
|---|---|
| Keep one manifest per stage (PRD as written) | Cannot describe a second DoD round or seven per-story units: roles repeat, so a correct run would fail AC-DISP (evidence: `-r2` files and `S1-S2-*` files above). |
| Allow repeated roles inside one manifest | Removes the very check (roles distinct) that detects a fused or duplicated dispatch. |
| Derive expected N from the config list only | Light stages legitimately dispatch fewer than the list (SKILL.md Light definition), and Stage 2 dispatched exactly the list; an equality rule would fail one of them. The bound is `N <= len(list)` and roles subset of the list. |
| Read `06-dev` per pipeline-stages.md | The PRD ACs and existing artifacts already use `06-development`; switching means rewriting AC paths. Logged as a reference-doc defect instead. |
| Parse config with PyYAML or `yq` | New dependency; BC-03 forbids it. |
| Branch protection or a server-side hook for the push | Out of scope (PRD section 10). |
| Run the gate from a clean `git worktree add` of the commit instead of requiring a clean tree | Adds worktree metadata to the shared `.git` and a second checkout to manage; the clean-tree test proves the same equality more cheaply, and the S7b fresh clone covers the committed-content scan independently. |
| Require a PR for the push so branch protection can gate it | Contradicts BINDING-5.1 (squash-rebase, ff-merge, push, no PR). It is the one option that would PREVENT rather than detect; recorded as accepted residual risk RR-1 (item 8) with an owner and revisit trigger, not adopted. |

## Consequences

- AC-DISP has more moving parts than the PRD's script: about 60 lines instead of 30. It still needs no dependency and carries a negative self-test.
- The ship path is detect-and-fix-forward for a pusher who skips the gate (RR-1, item 8); prevention is an owner decision, not part of this design.
- S7 grows a clean-tree step, an out-of-tree evidence log and an independent post-push dispatch (S7b, one more devops sub-agent, about one cheap run). That is the price of making the ship control objective; the alternative is a self-reported line.
- The S7 executor needs a manifest per unit (item 4b) and per extra round; the orchestrator must write them as it dispatches, or the ship gate fails loudly. That is the intent.
- If the PO prefers the PRD's one-file-per-stage form, the minimum change is to make the manifest describe only the final passing round of the stage and to drop the per-story requirement for `06-development`; the ADR then drops rules 4 and 5's per-story clause. Rule 5's role and length bounds remain valid either way.
