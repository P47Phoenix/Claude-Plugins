# ADR-004: Human-Execution Stage Orchestration Pattern

**Status:** Accepted
**Date:** 2026-04-12
**Deciders:** Solution Architect (Celebrimbor)
**Pipeline:** run-2026-04-12-hw01 | **Type:** GREENFIELD

---

> "There are works that no forge can accomplish without the smith's own hands upon the metal. The prototype must be built, the solder must flow, the test probe must touch the pad. These are acts of the physical world that no amount of architectural elegance can automate. We must design our pipeline to acknowledge this truth with grace."

---

## Context

Three of the 8 hardware pipeline stages involve physical activities that AI cannot perform:

- **Stage 4: Prototype** -- Ordering PCBs, assembling boards, running bring-up tests
- **Stage 7: Pilot Run** -- Small production run, assembly yield measurement, production test validation
- **Stage 8: Production Release** -- Full production handoff, manufacturing transfer, quality sign-off

The question is how the pipeline orchestrator should handle stages where the primary activity is performed by a human in the physical world, not by an AI agent.

## Decision

**Adopt the gate-in/human-action/gate-out orchestration pattern.** Each human-execution stage follows a three-phase flow:

### Phase 1: GATE-IN (AI generates preparation artifacts)

The orchestrator dispatches a sub-agent (typically Test Engineer or Manufacturing Engineer) that:
- Generates preparation documentation (ordering packages, test procedures, manufacturing transfer packages, production checklists)
- Produces structured action items for the human
- Saves all artifacts to `.hardware/artifacts/<stage-name>/`
- Presents output with a clear "HUMAN ACTION REQUIRED" block

### Phase 2: HUMAN-ACTION (pipeline pauses)

The pipeline transitions to `PAUSED_AWAITING_HUMAN` state:
- User receives numbered action items describing what to do physically
- Pipeline state is persisted to `.hardware/state.md` (survives session boundaries)
- User has three response options:
  - `"<stage> complete"` -- human action succeeded, proceed to gate-out
  - `"<stage> failed: <description>"` -- human action failed, trigger rework
  - `"save pipeline state"` -- pause for later resume

### Phase 3: GATE-OUT (AI evaluates completion)

Based on human response:
- **Complete**: Gate evaluates (checks artifact completeness, confirms all preparation items were addressed), pipeline advances
- **Failed**: Rework triggered using the standard rework path table; human checkpoint is INVALIDATED; existing preparation artifacts are ARCHIVED (moved to `archived/run-N/`, never deleted); target stage re-executes with failure description as context
- **Save**: State persisted, no gate evaluation, pipeline ready for resume

### Key Design Properties

1. **AI generates, human executes**: The AI's role is preparation and documentation, not physical action. The pipeline is honest about this boundary.
2. **State persistence across sessions**: Human-execution stages may span days or weeks (waiting for PCB fabrication, assembly). The pipeline must survive session boundaries.
3. **Artifact archival on rework**: When a human-execution stage triggers rework, the preparation artifacts from the failed attempt are preserved in `archived/run-N/` for reference. New preparation artifacts are generated after the rework target stage re-executes.
4. **Explicit checkpoint invalidation**: The checkpoint state machine (PENDING --> COMPLETED or INVALIDATED) makes it clear what happened during rework.

## Consequences

### What becomes easier

- **Honest automation boundary**: The pipeline does not pretend to automate physical work. Users understand exactly what they need to do.
- **Cross-session continuity**: Pipeline state persists through the multi-day gaps typical of hardware prototyping (order boards, wait for delivery, assemble, test).
- **Audit trail**: The state file records every human checkpoint with timestamp, status, and associated artifacts.
- **Rework clarity**: When a prototype fails, the failure description flows back to the target stage as specific context ("thermal issue on U3"), not a generic "try again."

### What becomes harder

- **User discipline**: The user must remember to confirm completion or report failure. If they forget, the pipeline remains paused indefinitely. Mitigated by the SessionStart hook detecting paused state on next session start.
- **Long pauses**: Pipeline may be paused for days or weeks. Config snapshot and artifact validation on resume mitigate drift.
- **Testing**: Human-execution stages cannot be fully automated in tests. The reference test fixture (Story 4.0) covers AI-execution gates; human-execution flow must be validated manually.

## Reversibility

**Two-way door.** This decision is reversible. Human-execution stages could be converted to AI-execution stages in the future if:

1. AI capabilities advance to simulate or validate physical outcomes (e.g., thermal simulation replaces thermal testing)
2. External automation tooling (robotic assembly, automated test equipment with API access) becomes available

The conversion cost is moderate: each human-execution stage's SKILL.md would need rewriting to remove the gate-in/human-action/gate-out pattern and replace it with standard AI-execution flow. The rework paths from human stages back to design stages would remain valid -- only the trigger mechanism changes (from human reporting failure to AI detecting failure). The state machine would simplify (no `PAUSED_AWAITING_HUMAN` state for converted stages).

This is a two-way door because the direction of conversion (human to AI or AI to human) can be applied per-stage independently.

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|---|---|---|---|
| Skip physical stages entirely (5-stage AI-only pipeline) | Simpler; fully automatable | Ignores the most critical feedback loop in hardware development (prototype results inform design iteration); users would still need to do physical work but without structured guidance | Hardware development fundamentally requires physical validation |
| Simulated physical stages (AI pretends to prototype) | Fully automated pipeline | Dishonest; AI cannot simulate real-world thermal behavior, assembly yield, or component compatibility; would produce false confidence | Violates engineering integrity |
| Physical stages as optional appendix (run separately) | Cleaner pipeline; no pauses | Loses the connection between prototype failure and rework; no structured rework path from physical stage back to design stage | The rework feedback loop from prototype to schematic is one of the plugin's core value propositions |
| Timeout-based advancement (auto-advance after N days if no response) | Prevents indefinitely paused pipelines | Dangerous; auto-advancing past a failed prototype could lead to wasted fabrication costs | Silent failure is worse than a paused pipeline |
